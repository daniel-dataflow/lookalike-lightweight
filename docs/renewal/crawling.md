# 크롤링 파이프라인 리뉴얼 및 안전 검증 설계 문서

본 문서는 Lookalike 프로젝트의 크롤링, 스테이징, 이미지 이관(Swap) 파이프라인 리뉴얼 과정과 세부 설계 변경 내용, 그리고 시스템 안정성을 확보하기 위한 **개발 및 테스트 분기 정책**을 기록하는 공식 기술 문서입니다.

---

## 📌 1. 아키텍처 개요 및 배치 프로세스

Lookalike 파이프라인은 크롤링 시점의 서버 부하를 최소화하고, 수집 데이터의 이미지 유효성과 정합성을 사전에 검증하여 무결한 데이터만 운영 DB에 반영하도록 설계되었습니다.

```mermaid
graph TD
    A[Phase 1: 크롤링 및 수집] -->|7일 주기 실행| B[(DW DB: staging_products)]
    B -->|임베딩 사전 추출| F[(DW DB: staging_product_embeddings)]
    F -->|Cloudinary staging/ 폴더| C{24시간 유예기간 대기}
    C -->|자동 스위칭 & 4대 에러 검증| G{에러 상품 격리?}
    G -->|Yes (자동 이관 배제)| H[Staging 대기 유지 / 에러 통제 탭 노출]
    G -->|No (정상 통과)| D[Phase 2: 이미지 이관 및 스위칭]
    H -->|운영자 수동 강제 이관 / 핀포인트 재수집 복구| D
    D -->|Cloudinary products/ 폴더| E[(PROD DB)]
```

### 1) Phase 1: 7일 주기 수집 및 임시 격리 (DW DB 적재)
* **주기**: 7일마다 1회 작동 (자동 배치 또는 어드민 수동 트리거)
* **역할**: 에잇세컨즈, 탑텐, 유니클로, 스파오, 지오다노, 폴햄 등의 브랜드 쇼핑몰에서 상품 상세 및 이미지를 크롤링한 뒤, 실시간으로 Cloudinary 임시 경로(`staging/{brand}`)에 업로드하고 **DW DB**의 `staging_products` 및 `staging_naver_prices` 테이블에 1차 격리 저장합니다.
* **YOLOv11 + Fashion-CLIP 사전 추출**: 수집과 동시에 각 상품 이미지를 YOLOv11 추론 서버(HF Spaces)에 통과시켜 불필요한 배경 노이즈를 제거(Pre-Cropping)한 뒤, 정확도가 극대화된 512차원 Fashion-CLIP 이미지 임베딩과 텍스트 임베딩을 백그라운드에서 병렬 생성하여 **DW DB의 `staging_product_embeddings` 테이블**에 사전에 보관합니다.
* **영향**: 이 단계에서는 사용자 화면(운영 DB)에 어떠한 데이터 변화도 주지 않아 크롤링 부하가 상용 서비스에 미치지 않습니다.

### 2) Phase 2: 에러 격리형 안전 스위칭 (Blue-Green Swap & Error Isolation)
* **주기**: 매일 새벽 5시 KST (또는 관리자 대시보드에서 수동 즉시 실행)
* **대상**: 스테이징 테이블에 적재된 지 **24시간이 경과한 데이터**
* **4대 치명 에러 진단 및 격리**: 
  - 이관 전 필수 메타 유실(`METADATA_LOSS`), 네이버 가격 5개 전무(`NAVER_PRICE_MISSING`), 임베딩 벡터 누락(`EMBEDDING_MISSING`), 이미지 링크 깨짐/이동 실패(`IMAGE_BROKEN`)가 감지된 상품들은 자동으로 이관 리스트에서 제외(Filter Out)되어 Staging에 격리 대기 상태로 유지되며, `pipeline_errors` 테이블에 세부 정보가 기입됩니다.
* **검증 및 스위칭 절차**:
  1. **정합성 검증**: 수량 임계치 검사(10건 미만 시 차단 의심 예외 발생), 불량 상품 정밀 스캔 및 격리 배제.
  2. **이미지 유효성 검증**: 비동기 HTTP 요청을 통해 이미지 URL의 활성 상태(HTTP 200 OK)를 딥 스캔.
  3. **Cloudinary 이미지 원격 이동**: 검증 완료 시 Cloudinary 상에서 정상 이미지를 `staging/` ➔ `products/` 폴더로 즉시 이동 처리.
  4. **임베딩 및 데이터 고속 복사**: DW DB의 `staging_product_embeddings`에 기추출되어 보관되어 있던 Fashion-CLIP 이미지 벡터와 텍스트 벡터를 고속 복사합니다.
  5. **트랜잭션 기반 스위칭**: 원자적 트랜잭션을 시작하여 운영 DB의 기존 브랜드 상품, 최저가, 임베딩 데이터를 제거(`DELETE`)하고 신규 정상 데이터를 일괄 적재(`INSERT`)한 뒤 커밋합니다.
  6. **복구 통제소 조치**: 격리 대기 상태인 오류 상품은 관리자가 어드민 "에러 상품 통제 & 복구" 탭에서 직접 개별 **[재수집]**을 찔러 실시간 API 복구(네이버 검색 호출 및 임베딩 갱신)를 하거나, 강제 이관(`partial_switch`), 스테이징 삭제(`delete_staging`) 등의 핀포인트 관제 조치를 취합니다.

## 🛠️ 2. 리팩토링 및 최적화 이력

크롤링 파이프라인의 이력을 순서대로 정렬하여 기록합니다.

### 1) 1차 리팩토링: Actions 기반 수집 분리 (2026-05-24)
* Render 무료 서버 부하 감소를 위해 크롤링 연산을 GitHub Actions 환경으로 완전히 이관하고 분리했습니다.
* CLI 엔트리포인트(`crawling_pipeline_cli.py`)와 임시 스테이징 테이블 연동 설계.

### 2) 2차 최적화: HDFS 의존성 제거 및 수집 캐시(CDC) 도입 (2026-05-28)
* 레거시 하둡(Hadoop) 및 HDFS 연동 모듈을 완전히 도려내고 PostgreSQL Neon DB 구조로 일원화했습니다.
* 캐시 데이터를 조회하여 가격 및 이미지에 변경이 없을 경우 Cloudinary 업로드를 생략하여 트래픽 비용 및 시간 단축.

### 3) 3차 리팩토링: 물리 DB 이중화 및 KST 서울 시간대 통일 (2026-05-30)
* Neon DB의 무료 플랜 용량(0.5GB) 한계를 지키기 위해 메인 `PROD DB`와 `DW DB`로 데이터베이스 커넥션을 물리적으로 완벽히 분리했습니다.
* 모든 DB 커넥션 세션 연결 시 `SET TIME ZONE 'Asia/Seoul';`을 강제 주입하여 시간대를 서울로 동기화했습니다.

### 4) 4차 최적화: 어드민 스위칭 런타임 오류 해결 (2026-06-04)
* 백엔드 API 서버(`admin.py`)에서 `data-pipeline` 내의 `base_utils`를 로드하기 위한 절대 경로 산출법으로 전면 수정했습니다.
* 실행 가상환경(`ml-env`) 상의 누락 패키지(`aiohttp`) 설치를 연동하고, 임시 테스트 스위칭 대기 시간을 설계 스펙인 24시간(`hours_elapsed < 24`)으로 원복 적용했습니다.

### 5) 5차 리팩토링: YOLOv11 + Fashion-CLIP 사전 임베딩 추출 설계 (2026-06-05)
* 수집 시점에 대량의 임베딩을 선 생성하여 **`DW DB` 내의 `staging_product_embeddings` 테이블**에 사전 보관하도록 프로세스를 고도화했습니다.
* 이로 인해 스위칭 시점에는 DW DB에 이미 적재된 벡터들을 대상 운영/테스트 DB로 단순 쿼리 복사(`INSERT`)하여 초고속 스위칭이 가능해졌습니다.

### 6) 6차 최적화: 환경 변수 공백 제거 및 미사용 레거시 파일 정리 (2026-06-08)
* `.env` 파일의 `DEV_CLOUDINARY_...` 환경 변수의 등호 전후 공백을 제거하여 파싱 오류를 해결하고 레거시 변수를 정리했습니다.
* `scripts/supabase`에 이중 저장되어 혼선을 주던 스키마 DDL 폴더를 삭제하고, 루트의 `supabase/migrations`로 합병 단일화했습니다.

### 7) 7차 리팩토링: 모니터 대시보드 리뉴얼 및 긴급 단일 재수집 (2026-06-16)
* 자동 크롤링 모니터링 탭을 읽기 전용 대시보드로 개편하고, 실시간 스캔 결과 총량 대비 수집 현황 게이지바를 연동했습니다.
* 에러 로그 클릭 시 예외 원인을 표시하는 '에러 정밀 진단 모달'을 추가하고, 실패한 특정 상품 1건만 단독으로 타겟팅하여 가상환경(`ml-env`)에서 즉각 백그라운드로 수집을 재수도하는 연동 기능을 탑재했습니다.

### 8) 8차 최적화: 스파오 수집 실패 해결 및 임베딩 3중 안전망 구축 (2026-06-24)
* **스파오(SPAO) 상세 수집 리다이렉트 해결**: 상세 페이지 URL 구성 시 `itemNo`뿐만 아니라 `lowerVendNo`를 함께 추출하도록 크롤러 파싱 로직을 고도화하여 리다이렉트로 인한 수집 스킵 버그를 제거했습니다.
* **네트워크 3중 재시도 로직**: 이미지 다운로드 3회 재시도 및 Gradio API 2회 호출 재시도를 구현하여 에러율을 최소화했습니다.
* **로컬 CLIP 모델 이미지 임베딩 폴백(Fallback)**: API 서버 장애나 YOLOv11 크롭 실패 시 `image_vector`가 `NULL`로 수집되는 현상을 막기 위해, 실패 발생 시 자동으로 로컬 캐시 모델(`openai/clip-vit-base-patch32`)을 가동하여 **원본 이미지 전체에 대해 로컬에서 직접 512차원 임베딩을 생성**해 적재하는 자동 방어막을 구축했습니다.

### 9) 9차 고도화: 통합 에러 상품 통제 및 핀포인트 복구 대시보드 구축 (2026-06-30)
* **4대 치명 에러 자동 진단 및 이관 배제**: 스위칭 처리 과정에서 필수 메타 유실(`METADATA_LOSS`), 네이버 가격 전무(`NAVER_PRICE_MISSING`), 임베딩 유실(`EMBEDDING_MISSING`), 이미지 링크 깨짐/이동 실패(`IMAGE_BROKEN`)를 검출하여 `pipeline_errors` 테이블에 상품 ID와 상세 원인을 기록하고, 자동 이관(`force=False`) 시 이들 에러 상품만 핀포인트로 이관 배제 처리하여 Staging 테이블에 대기 보존하도록 구현했습니다.
* **핀포인트 1초 즉시 복구 API 및 단일 재수집 버튼 신설**: 에러 상품 리스트 우측에 `[재수집]` 버튼을 추가하여, 단일 상품에 대해 네이버 쇼핑 OpenAPI 실시간 최저가 수집(상위 5개) 및 CLIP 임베딩 연산을 원스톱으로 즉시 재실행하여 에러를 자동 복구하고 소거하도록 설계했습니다.
* **어드민 벌크 통제 액션 바인딩**: 어드민 화면에 "에러 상품 통제 & 복구" 탭을 신설하고, 다수 상품을 체크박스로 다중 선택하여 일괄 강제 이관(`partial_switch`), 벌크 가격 재수집(`re_crawl`), 임베딩 재생성(`re_embed`), 또는 스테이징 영구 삭제(`delete_staging`)를 수행하는 벌크 관리 인프라를 완성했습니다.

### 10) 10차 고도화: 크롤링 모니터링 화면 개편 및 프론트엔드 리소스 삼단 분리 (2026-07-03)
* **대기 vs 운영 2열 대조 대시보드 구축**: 크롤링 모니터링 화면 내 브랜드별 상품 카드를 대기 상품 수(Staging)와 운영 상품 수(Prod)를 2열 대칭 구조로 개편하여 적재 불균형 상태를 한눈에 볼 수 있도록 시각화하였습니다.
* **지표별 누락 정합성 경고 색상 분기**: 수집 완료율 및 4대 정밀 지표(임베딩, 네이버 최저가, 이미지 수량) 누락 비중에 맞춰 0% 초과~20% 미만 누락은 주황색 폰트 컬러로, 20% 이상 누락 시에는 옅은 핑크색 배경 배지와 진한 빨강 폰트 컬러로 차별화된 경고 피드백을 제공합니다.
* **프론트엔드 HTML/CSS/JS 완전 삼단 분리**: 어드민 크롤링 관리 화면(`admin_crawling.html`) 내에 섞여 있던 대량의 인라인 스타일과 스크립트를 독립 정적 자원(`admin_crawling.css`, `admin_crawling.js`)으로 완전히 추출하여 1:1 파일명 매칭 구조로 소스 관리를 정돈하였습니다.

## 🔒 3. 개발 및 테스트 보안 격리 정책

### 1) DEV vs PROD 역할/용량 분담형 멀티 DB 아키텍처
* **개발/테스트 세트 (`APP_ENV=local` 또는 `dev`)**:
  - `DEV_DATABASE_URL` (개발용 메인/세션 DB): 듀프 패션 매칭 실시간 검색 서비스에만 집중하여 초고속 인덱스 연산을 보장합니다.
  - `DEV_DW_DATABASE_URL` (개발용 수집/격리 DB): 크롤러가 수집한 대규모 스테이징 원본(`staging_`)과 배치 로그, 임베딩을 보관하여 메인 운영 DB의 스토리지 용량 고갈을 방지합니다.
  - `DEV_TEST_DATABASE_URL` (개발용 스위칭 모의 테스트 DB): 실서버 적재 전, DDL 정합성 및 Blue-Green 이관 검증을 독립적으로 수행하는 샌드박스 DB입니다.
* **운영 세트 (`APP_ENV=prod`)**:
  - `PROD_DATABASE_URL` (상용 서비스 및 사용자 세션 라이브 DB): 순수 매칭 서비스 노출용 products 레코드만 보관합니다.
  - `PROD_DW_DATABASE_URL` (운영 배치를 위한 임시 데이터 격리 및 로그 DB): 수집 데이터를 실 운영망과 분리하여 관리합니다.
  - `PROD_TEST_DATABASE_URL` (운영용 스위칭 안전 검증 격리 DB): 실제 배포 전 최종 검증용 샌드박스 DB입니다.

### 2) Cloudinary 이미지 서버 로컬 및 환경 격리 (최상위 분리)
* 하나의 Cloudinary 공간을 공유하며 발생하던 폴더 오염과 이미지 유실을 예방하기 위해, 최상위 경로를 통해 **개발(DEV) 이미지 저장소**와 **운영(PROD) 이미지 저장소**를 완전 이중화했습니다.
* **DEV 환경**: 이미지 업로드 시 Cloudinary 최상위 폴더가 `DEV/` 하위로 적재됩니다.
  - 임시 적재: `DEV/staging/{brand}/`
  - 검증 이관: `DEV/test/{brand}/` 또는 `DEV/products/{brand}/`
* **PROD 환경**: 이미지 업로드 시 Cloudinary 최상위 폴더가 `PROD/` 하위로 적재됩니다.
  - 임시 적재: `PROD/staging/{brand}/`
  - 검증 이관: `PROD/test/{brand}/` 또는 `PROD/products/{brand}/`

## 📊 5. 크롤링 모니터링 화면 표시 및 정합성 검증 규칙

크롤링 관리 대시보드에서 수집 및 운영 데이터 적재율을 시각적으로 모니터링하고 데이터 유실 여부를 즉각 감지하기 위한 표준 렌더링 규격입니다.

### 1) 2열 대조 카드 레이아웃
* 각 브랜드별 상태 카드는 좌측에 **수집 대기(Staging) 상품 수**, 우측에 실제 **운영(Prod) 상품 수**를 2열 대치하여 표시합니다.
* 각 상품 수 수치 하단에는 해당 상품군에 적재 완료된 세부 지표 수량을 대기 vs 운영의 매칭 구조로 배치합니다.
  * **임베딩(벡터) 수량** (목표치: 상품 수와 1:1)
  * **네이버 최저가 5선 수량** (목표치: 상품 수의 5배, `count * 5`)
  * **이미지 수량** (목표치: 상품 수와 1:1)

### 2) 네이버 최저가 분모 보정 연산식
* 네이버 쇼핑 최저가는 상품 1개당 최대 5개 비교 매장 가격을 수집하여 1:N 구조로 누적 관리하므로, 최저가 수집의 완전성(100%) 검증을 위한 목표 분모 기준값은 **`상품 수 * 5`** (`staging_count * 5` 및 `prod_count * 5`)로 적용하여 분할 연산합니다.

### 3) 지표 누락률별 주황/빨강 워닝 경고 시스템
수집 목표량 대비 실제 적재된 하위 지표(임베딩, 최저가, 이미지) 수량에 누락이 감지되면 직관적인 시각 피드백을 활성화합니다.
* **주황색 경고 (0% 초과 ~ 20% 미만 누락)**:
  * 폰트 색상을 진한 다크 오렌지(`#ea580c`) 컬러로 강조하여 경미한 누락이 발생했음을 인지시킵니다.
* **빨간색 경고 (20% 이상 누락 - 심각)**:
  * 폰트 색상을 진한 딥 레드(`#b91c1c`) 컬러로 변경하고, 배경에 옅은 핑크색 라운드 박스 배지(배경 `#fee2e2`, 테두리 `#fca5a5`, 안쪽 여백 부여)를 씌워 즉시 크롤러 재수집 조치가 필요한 심각한 유실 상태임을 부각시킵니다.

### 4) 데이터 없는 브랜드 숨김 필터링
* 등록된 총 8개 브랜드 중 수집 대기 상품(Staging)과 운영 상품(Prod) 수량이 모두 0인 비활성 브랜드는 대시보드 가독성을 위해 기본적으로 화면에서 숨김(`window.hideEmptyBrands = true`) 처리합니다.
* 관리자가 필요한 경우 상단의 토글 버튼을 클릭하여 전체 브랜드를 펼쳐볼 수 있습니다.

## 📂 6. 프론트엔드 소스 관리 표준 가이드라인

웹 서비스 리팩토링 및 신규 페이지 추가 시 코드의 가독성과 파일 탐색 일관성을 보장하기 위한 프론트엔드 리소스 설계 표준입니다.

### 1) 1:1 동일 파일명 매핑 규칙
각 화면에 링킹되는 정적 스타일(CSS)과 비즈니스 스크립트(JS)는 관리 용이성을 극대화하기 위해 HTML 파일과 **완벽히 동일한 베이스 파일명**을 사용하여 경로를 매핑합니다.
* **경로 구조**:
  * 템플릿(HTML): `web/frontend/templates/[파일명].html`
  * 스타일(CSS): `web/frontend/static/css/[파일명].css`
  * 스크립트(JS): `web/frontend/static/js/[파일명].js`
* **예시**: `admin_visitors.html` 은 무조건 `admin_visitors.css` 및 `admin_visitors.js` 파일만 참조합니다.

### 2) Jinja2 동적 템플릿 변수의 HTML 데이터 바인딩 우회
* 외부로 독립 분리된 `.js` 파일 내부에서는 백엔드 렌더러가 해석하는 Jinja2 변수(`{{ query }}`, `{{ product.product_id }}` 등)를 직접 하드코딩해 사용할 수 없습니다.
* 이를 해결하기 위해 HTML 파일 내 루트 엘리먼트에 `id`와 `data-*` 속성(예: `data-product-id="{{ product.product_id }}"`) 형태로 서버 사이드 변수를 미리 심어둡니다.
* 분리된 JS 파일에서는 `DOMContentLoaded` 이벤트 시점에 해당 엘리먼트를 선택한 후, 브라우저 표준 `dataset` API를 통하여 안전하게 동적 변수값을 추출·바인딩하도록 설계 구조를 통일합니다.

### 3) 정적 자원 캐시 갱신 전략 (Cache Busting)
* 브라우저의 강력한 정적 자원 캐싱으로 인해 리팩토링 배포 후에도 화면 디자인이 깨지거나 구 버전 스크립트가 실행되는 오작동을 차단하기 위해, HTML 내 파일 링킹 부에 난수 기반의 캐시 버스터 파라미터를 강제 적용합니다.
* **코드 예시**:
  ```html
  <link rel="stylesheet" href="/static/css/파일명.css?v={{ range(1, 999999) | random }}">
  <script src="/static/js/파일명.js?v={{ range(1, 999999) | random }}"></script>
  ```
